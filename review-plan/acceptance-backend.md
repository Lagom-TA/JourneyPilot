## 需要知晓的事项

<a id="r-01"></a>
**R-01 记忆事实的单值冲突按创建时间比较。** 预算上限、节奏偏好这类单值冲突，仲裁顺序是：本次请求顺序 → `updated_at` → 来源权威度 → 是否硬约束。记忆事实的 `updated_at` 取自 `created_at`，而 `memory_facts` 没有更新时间列，所以 B5-12 原地更新过的事实仍按首次创建时间参与比较。只有“两条不同的记忆事实产出同一个单值类别，且较早创建的那条被新意愿更新”时，才会选中较旧的意愿。场景窄，且总结会同时看到两条事实；修复需要新增列和迁移，验收阶段没有处理。

<a id="r-02"></a>
**R-02 `infra/compose.yml` 有一处自 S0 起未提交的改动**，已转入待决事项 [D-08](decisions.md)。它让 PostgreSQL 宿主端口读取 `JOURNEYPILOT_DATABASE__PORT`（默认仍为 55433）；现有 `journeypilot-postgres` 容器（55434）正是据此创建的，而已提交版本写死 55433，该端口现在被另一个项目的容器占用。验收没有替用户提交它。

<a id="r-03"></a>
**R-03 整镜像未能在本机完整构建，这是验收中唯一没有闭合的验证。** 本机网络下官方源构建做不完（Debian 源长时间停滞，npm 连接中断）；改用镜像源副本（仓库里的 Dockerfile 未改动）后：

- 已验证：Python 核心依赖层按 `uv.lock` 冻结安装成功，依赖可导入；Node MCP 阶段用当前锁文件安装，在断网的 Linux 容器（aarch64、Node 22.23.4）中，5 个 Node 服务全部完成 JSON-RPC 握手并列出工具；`docker compose config` 对已提交与未提交两个版本都能解析。
- 未验证：前端阶段在 Docker 内的 `npm ci`（两次因 npm 自身崩溃失败；同样的命令在干净 HEAD 副本里通过），以及运行层装配与入口。
- 依据：`infra/api.Dockerfile`、入口脚本、`.dockerignore` 与依赖清单自基线以来没有变化；B6 已用镜像源完成过整镜像构建并通过入口、API、网页检查；CI 的 `docker` 作业会在每次 PR/推送时用官方源构建默认镜像（含 `local-embedding`），并执行配置校验、Node 版本、静态页面、`pg_dump` 等检查。**整镜像的最终证明应由下一次 CI 运行给出。**
- 副作用与清理：这几轮构建让数据盘一度只剩约 0.6 GB。已删除我创建的镜像，并清空了 JourneyPilot 审查期间产生的构建缓存（4.1 GB，纯缓存，仅影响下次构建速度），盘空闲恢复到约 6.5 GB。今后在本机构建镜像需要镜像源（B6 用过清华 apt 源与腾讯 npm 镜像），`uv` 还需调大 `UV_HTTP_TIMEOUT`，并在构建后清理缓存。
