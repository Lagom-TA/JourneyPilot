# 工作规则

[返回总览](../REVIEW-PLAN.md)

## 一个阶段一个闭环

1. **开工**：在总览表把状态改为 🔍，填上负责人（前端页面阶段写“采集 / 分析”两人）。先逐条处理阶段文件中的“收到的提醒”。
2. **审查**：按阶段文件的“审查项”逐项检查并勾选。问题记入该文件的“问题与修复”，编号用 `阶段-序号`（如 `B2-03`）。前端页面阶段按下面的[前端交接](#前端页面阶段的交接)进行。
3. **修复**：本阶段发现的问题在本阶段内修完并自测，状态改为 🔧。需要产品取舍的问题写进[待决事项](decisions.md)，其余问题照常修复，不等待。
4. **提醒**：每修完一项，对照阶段文件的“影响下游”，在每个受影响阶段文件的“收到的提醒”里追加一条；受影响的阶段如果已完成，在总览表把它的状态改为 ↩️。
5. **收尾**：问题全部关闭或已转入待决事项后，状态改为 ✅，在总览表填写完成日期和提交号，并更新各阶段的“未处理提醒”数。

## 前端页面阶段的交接

采集和分析由不同的模型完成，两者只通过素材包交接：素材放在 `output/review/<阶段>/`，清单是 `manifest.md`。

| 步骤 | 谁做 | 做什么 | 交出什么 |
|---|---|---|---|
| 采集 | 采集员 | 按阶段文件的截图清单、录屏清单，以及需要操作才能看到的审查项拍摄 | 素材和清单；截图清单的“进度”改为 📸 |
| 分析 | 分析员 | 只依据素材和清单判断 | 问题写入阶段文件；缺少的素材写成补拍请求；“进度”改为 👁 |
| 修复 | 采集员 | 按问题修改代码并自测 | 在问题行写上提交号；“进度”改为 🔧 |
| 复拍 | 采集员 | 只重拍受影响的场景 | `-r1`、`-r2` 素材，清单里新增对应行 |
| 复核 | 分析员 | 对照新旧素材 | 勾选已关闭的问题；场景全部关闭后“进度”改为 ✅ |

具体做法见[采集规范](capture.md)和[分析规范](analysis.md)。F1 以读代码为主，由采集与修复一侧完成。

## 边界

- 只修本阶段范围内的问题。发现其他阶段的问题，写进那个阶段文件的“收到的提醒”，不要顺手修改。
- 本地服务、数据库和破坏性操作遵守根目录的 `AGENTS.md`：使用当前配置的数据库；删除、清空或重建数据之前，先取得授权。
- 本机整个定版审查共用现有的 `journeypilot-postgres`、宿主端口 `55434` 和持久卷 `journeypilot_postgres_data`。启动时带 `JOURNEYPILOT_DATABASE__PORT=55434`；不要为不同阶段新建、切换或删除数据库。现有会创建并删除临时数据库的测试夹具不用于本次审查；必要的数据库验证在这套库中使用临时表与回滚事务，不修改既有记录。
- 调用付费模型或收费的外部服务之前，先取得授权。
- 阶段文件只记结论：一个问题一行，一次修复一行，一条提醒一行，不写过程。

## 记录格式

```markdown
问题与修复：- [ ] B2-03 问题描述 → 修复方式（提交 abc1234）
前端问题：  - [ ] F3-02 〔G5-D-running.png〕问题描述 → 修复方式（提交 abc1234）→ 复核〔G5-D-running-r1.png〕
收到的提醒：- [ ] 来自 B2-03：改了什么 → 请复核什么
待决事项：  | D-01 | B2-03 | 需要决定的事 | 结论 |
```

素材清单和补拍请求的格式见[采集规范](capture.md#素材清单)。
