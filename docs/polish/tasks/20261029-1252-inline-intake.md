## 2 现象与发生条件

首页条件规划或卡内需求确认 → 点击开始/最终确认 → 正式规划工作区。用户观察到中间闪过另一页面，终点是失败状态的生成进度工作区。指挥已在 2000×880、正常 motion、恢复未完成 intake 的离线夹具复现中间聊天态；全部 API 拦截，无后端或模型请求。还需覆盖全新条件规划入口、reduced-motion、首个 SSE 延迟及启动失败。

## 3 根因

当前代码已保留首页卡内需求确认，本轮问题位于确认后的布局交接：

- `TripWorkspaceShell.tsx:35–36、60–68` 以“已有 Run ID 且有受控身份”切换布局，外层 `AnimatePresence mode="wait"` 在切换后仍保留会话布局的退出帧。
- `ConversationThread.tsx:53、69–70、129` 同时读取新的工作区条件；Run ID 到达后，退出中的旧组件立即把首页 body 换成普通聊天内容和底部输入栏，再被父层移除。指挥逐帧 DOM 采样在点击后约 532ms 观察到 `home=false`、旧会话帧仍存在、`aria-hidden=true`、`opacity=1` 且含聊天 textarea；约 712ms 旧帧才移除，规划工作区出现。这个约 180ms 的退出存活窗口已实际复现中间布局。
- 复现脚本与结果：`output/polish/20261029-1252-inline-intake/commander-transition-probe.mjs`、`commander-transition-probe.json`。脚本使用真实 UI、合成恢复草稿和浏览器内 API 拦截，页面错误为空；证明的是前端交接问题，不代表真实规划已成功。
- `GuidedIntakeQuestions.tsx:306–325、347–365` 正常 motion 下先收成准备卡并固定等 450ms，再发送规划请求；`useSendMessage.ts:49–58` 写入消息/身份，`streamEvents.ts:94–108` 收到 `chat_start` 后才清空 intake 并设置 Run。当前卡片收起动画与父层布局切换分开控制，已有动画不等于完整交接连续。
- `frontend/e2e/planner-intake.spec.ts:95–116` 主要检查收小和最终计划门可见，未证明退出窗口内从未出现聊天布局。计划门属于架构要求的独立审批，不能把它当作多余中间页直接删除。
- 另一个独立等待窗口是 `chat_start` 已到但首个 `agent_progress` 未到：后端 `conversation/chat/execution.py:215–221` 先发运行标识再启动 workflow，`ThinkingChain.tsx:121、131` 此时可能显示“准备旅行查询”空态。它属于新工作区内部的真实准备状态，应有连续反馈，不与旧会话退出期的闪页混为一谈。

## 4 方案

目标状态：用户确认后，原首页/确认卡平滑收拢并直接进入同一趟旅行的规划工作区；等待真实运行标识期间也有连续的原页面反馈，无普通聊天页、空白页或独立过场页闪现。实际计划门在规划工作区内照常等待批准。

必须做：

- 先用离线请求/事件夹具录下真实交接，确定中间出现的 DOM 分支。修复布局责任方的展示连续性，清除确认路径中的多余中间分支；其他会话仍需使用的聊天组件不能整文件删除。
- 原页面退出期间保持其当前内容稳定，避免因新状态到达而先重绘为另一种页面。首页到新工作区的离场、入场和必要的尺寸变化协调为一次连贯过渡；不得只增加固定等待来掩盖闪页。
- 首个 `chat_start` 延迟时保留原卡内的明确准备反馈，不提前伪造 Run 或 research 阶段；运行标识已到但首条进度未到时，在新工作区内维持准确、连续的准备反馈，不额外跳到另一整页空态。失败时按实际是否已有 Run 归属保留可重试草稿或展示失败工作区，不能丢失信息或重复提交。
- reduced-motion 下跳过大幅移动和人为等候，依然直接交接；正常 motion 的焦点落到新工作区的合理位置，避免停在卸载的按钮。
- 保留前轮已通过的卡内理解/逐题作答/修改/补充/保存、恢复未完成 intake、失败重试，以及异步 session/epoch/mounted 归属检查。切到另一趟旅行后旧保存/动画/流事件不能污染当前页面。
- 保留计划门 approve/edit/supplement/cancel 的真实审批语义，不自动批准、不跳过；确认规划与确认调研仍按现有合同完成。

执行者自己决定：局部交接状态与组件边界、布局动画方式、时长和焦点落点，优先复用现有 motion/PresenceSurface。卡内紧凑准备反馈可以保留为原卡的一种形态，不额外增加独立过场页面。

不许碰：后端理解/问题生成、API/SSE 契约、持久化语义、计划门批准规则、运行事实与无关导航。不提交不推送。

## 6 验收标准

### 6.1 代码验收（指挥检查）

1. 从条件规划直接开始，以及卡内最终确认两条入口，到正式工作区前后没有普通聊天布局、底部聊天输入栏、空白中间页闪现；慢首帧时仍保留原卡的准备反馈。
2. 正常 motion 下收拢、离场与工作区出现连贯，reduced-motion 无固定延迟或大幅位移；焦点可用。
3. 启动失败可按实际归属重试且已填信息不丢；准备期间切换旅行后没有旧请求或旧动画回写；必要计划门与历史会话功能不回归。

### 6.2 必须运行的检查

在 `frontend/` 下运行：

- `npm run type-check`
- `JOURNEYPILOT_APP_URL=http://127.0.0.1:8088 npx playwright test e2e/planner-intake.spec.ts --workers=1`
- `JOURNEYPILOT_APP_URL=http://127.0.0.1:8088 npx playwright test e2e/home-inspiration.spec.ts --grep '提交|规划|确认' --workers=1`
- `JP_SESSION_STATE_E2E=1 JOURNEYPILOT_APP_URL=http://127.0.0.1:8088 npx playwright test e2e/session-state.spec.ts --grep 'generation|规划|恢复|刷新|切换|确认' --workers=1`

为两条入口增加即时/延迟首帧、正常 motion/reduced-motion、失败与切换的定向交接检查；至少将一条合成 SSE 分段为“发 `chat_start` → 暂停 → 发首个 `agent_progress`”，分别观察旧会话退出与新工作区等待进度的窗口。用持续到退出动画结束的 DOM 观察或逐帧证据证明没有中间聊天布局，不能只断言最终页或 is-collapsing class。保留计划门直到用户真实审批。检查必须实际匹配到相关用例，按实际用例名细化 grep。全部离线拦截 `/api/`，不请求模型或写真实会话，端口以实际 Vite 服务为准。

### 6.3 实屏证据（执行者提供）

2000×880 正常 motion 的“确认前 → 原卡收起/等待 → 规划工作区”短录像或连续帧；附覆盖退出存活窗口的 DOM 分支记录。390×844 reduced-motion、延迟首帧与失败恢复各提供必要证据。存本任务 output 目录，文件名区分本轮。

### 6.4 真人验收（用户操作）

1. 首页按条件填好并开始规划 → 原页面连续过渡到规划页，中间不再闪过聊天或另一页。
2. 首页一句话规划，完成卡内问题并确认 → 卡片收拢后直接进入规划工作区，等待首帧时也不跳页；如出现计划门，仍可正常确认调研。
3. 系统开启“减少动态效果”后重复 → 直接交接，无人为等待和大幅动画。
