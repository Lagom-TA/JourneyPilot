# JourneyPilot 体验优化工作目录

用户反馈旅行工作台的体验问题后，指挥分析根因、编写任务方案；执行者依据任务文档实现并自测；指挥进行代码验收，用户进行实际体验验收。本目录是两者共用的流程规则，任务结构见[任务模板](template.md)。

## 目录

| 路径 | 内容 |
| --- | --- |
| `docs/polish/tasks/<编号>.md` | 一项任务一份；编号为 `YYYYMMDD-HHMM-英文短名` |
| `output/polish/<编号>/` | 反馈截图与实屏证据；`output/` 已被 Git 忽略 |

任务状态只写在任务文档开头的“状态”行。验收通过后保留任务记录；如用户明确要求提交，按用户要求及工作区实际情况处理提交和归档。

## 角色

- **用户**：反馈问题、提供必要的上下文并进行体验验收。
- **指挥**：分析根因、拆分任务、编写方案与验收标准、进行代码验收并记录用户验收；不改产品代码。
- **执行者**：阅读任务文档，自主选择实现方式，完成改动、自测并记录结果。多人或多个工具协作时，先明确文件所有权，避免覆盖已有改动。

## 状态

| 状态 | 设置者 | 含义 |
| --- | --- | --- |
| 待执行 | 指挥 | 方案已写好，可交给执行者 |
| 执行中 | 执行者 | 已开始本轮 |
| 受阻 | 执行者 | 遇到停止条件，记录问题，等指挥决定 |
| 待代码验收 | 执行者 | 本轮完成，执行记录已写全 |
| 返工 | 指挥 | 验收未通过，返工项写在“指挥验收” |
| 待真人验收 | 指挥 | 代码验收通过，等用户验收 |
| 已验收 | 指挥 | 用户验收通过，任务记录保留 |
| 搁置 | 指挥 | 用户决定暂缓 |

## 执行者须知

1. 先读任务文档全文、适用的仓库说明，以及与任务相关的 `docs/invariants.md`、`frontend/README.md` 或 `backend/tests/README.md`。有适用的 `AGENTS.md` 时一并遵守。任务文档应提供开工所需信息，不依赖其他会话的聊天上下文。
2. 开始时把状态改为“执行中”，在“执行记录”新建本轮小节。返工轮先读“指挥验收”和“真人验收”里的最新返工项。
3. 实现方式由执行者决定，完成“必须做”并遵守“不许碰”；沿前端组件、状态、API／SSE 和后端责任模块定位实际责任方，避免扩大范围。保留工作区已有改动，修改前先核对相关文件。
4. 遇到以下情况停止并将状态改为“受阻”，在本轮记录写清发现与需要决定的事：
   - 实际根因与任务文档不符，或按方案修改会引入新问题；
   - 需要超出任务授权修改数据模型、持久化、公开 API／SSE 契约、旅行预算规则或外部服务行为；
   - 验证需要调用真实付费模型、写入或删除真实用户数据，而任务未明确授权；
   - 需要触碰“不许碰”的内容，或任务文档列出的其他停止条件出现。
5. 只修改本任务文档的“状态”行和“执行记录”，不改其他章节。
6. 运行第 6.2 节列出的针对性检查，如实记录命令与结果；未运行的检查说明原因。后端测试策略见 `backend/tests/README.md`，前端命令见 `frontend/README.md` 与 `frontend/package.json`，浏览器测试和真实服务调用范围见 `frontend/e2e/README.md`。跳过的检查不算通过。
7. 需要实屏证据时，先确认现有服务和测试数据是否适用；按项目 README 使用 `./run.sh` 或前端开发服务器，地址和端口以实际配置为准。截图存入 `output/polish/<编号>/`，不要将密钥、会话数据或私人信息写入任务文档或提交。
8. 不提交、不推送、不切分支、不 stash；不覆盖或清理与本任务无关的工作区改动。
9. 完成后把状态改为“待代码验收”。

执行记录每轮格式：

```markdown
### 第 N 轮 · YYYY-MM-DD HH:MM · 工具／模型

- 改动摘要：
- 改动文件：
- 偏离方案及理由：（没有写“无”）
- 实际运行的检查与结果：
- 实屏证据：（路径；不需要写“不需要”）
- 遗留问题或需要指挥决定的事：（没有写“无”）
```

## 验收与关闭

- **代码验收**：指挥对照任务方案、执行记录和工作区差异，核对根因、边界、检查与截图；必要时抽查关键检查。通过后交用户体验验收，不通过则记录返工项。
- **真人验收**：用户按第 6.4 节操作。未通过时，指挥记录用户反馈，必要时修订方案并写入返工项；通过后将状态改为“已验收”。
- **提交与归档**：仅在用户明确要求时提交或归档。暂存前核对每个文件及其中的既有改动，不把其他任务的修改混入提交。长期有效的产品和工程规则写回相应的项目文档。
