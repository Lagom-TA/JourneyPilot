# 旅行规划内容质量：竞品、成品与现有架构诊断

研究日期：2026-10-08。本文保留研究时的诊断与建议；后续已实施修复并开展真实生成，进展与证据见 [实施与真实运行记录](implementation-results.md)。研究样例不构成同配置质量对照实验。

## 结论

当前证据支持一个较具体的判断：JourneyPilot 已建立候选事实、用户意图和交付结构的约束，但对**多个选择组成一趟旅行之后的体验质量**，还缺少充分的决策与验收反馈。目前不宜假设仅靠增加景点、润色报告或调整提示词即可解决，需要与流程改造做对照。现有营业时间与交通接续校验应保留；优先补足每日设计、区域组合、节奏、取舍和实际行动说明。

这不是“原架构全部错误”的结论。下面区分源码事实、实际输出观察与待验证假设。两份苏州样例不能估计产品整体失败率，也不能证明某个排序字段就是某次输出的根因。

## 研究范围与证据方法

围绕三个问题检索：优秀旅行成品包含哪些决策？公开产品如何支持这些决策？JourneyPilot 哪些环节没有稳定表达或验证它们？

采用中英文定向检索与原文阅读，查询覆盖 `Wanderlog route optimization travel times`、`Mindtrip itinerary`、`TripGenie itinerary features`、`马蜂窝 AI 路书`、`官方 旅游 路线 时长 公里`、`Kyoto itinerary`、`Rick Steves itinerary`、`TravelPlanner constraints`，另检索闭馆、交通估算不准等反证。纳入产品官方帮助、开发者发布、完整公开路线、场馆规则和原始研究；排除仅有搜索摘要、无法读取正文和不明来源的营销汇编。不报告无法复现的搜索总命中数；这是一轮产品研究，非穷尽式系统综述。

证据分四类，不能互相替代：

- **产品官方说明**：证明公开提供或宣称过某能力，不能证明算法或当前输出质量。
- **旅行成品**：可观察内容组织与决策方式，不能直接当实时事实或唯一正确答案。
- **运营规则**：只能用于适用地点、日期与人群；新公告可能覆盖常规规则。
- **本地源码与交付物**：证明当前实现/样例中的具体行为，因果归因仍需要对照实验。

来源及限制见 [sources.md](sources.md)。本次使用 AI 辅助检索、提取和分析；没有登录竞品进行同题实测，没有读取私人游记或复制整篇攻略。

## 竞品与成品应该分别学什么

| 参考对象 | 公开证据中的能力/组织方式 | 对我们的启发 | 不应直接推断 |
|---|---|---|---|
| Wanderlog | 行程地图、相邻点交通时长、路线优化 [S01–S03] | 把空间与交通代价放入选择过程，并让用户看到 | 有优化按钮就能保证全天可行 |
| Mindtrip | 兴趣输入与旅行者/目的地内容结合 [S04] | 候选内容需要体验理由与适用人群，不能只有地点事实 | 平台有大量来源就没有幻觉 |
| TripGenie | 节奏偏好、已订机酒输入、协作修改 [S05] | 固定订单、自由时间和偏好应参与同一个计划 | 官方更新等于当前版本实测 |
| 马蜂窝 | 从游记/笔记提炼行程和避坑信息 [S06] | 研究应同时抽取“值得做什么”和“不适合什么情况” | 热门游记天然准确、可直接复制 |
| 小艺旅行规划 | 按天地图和服务预订跳转 [S07] | 输出需要通往真实下一步操作 | 地图可画出来就可以执行 |
| 香港塔门路线 | 岛上时长、距离/难度、往返船程与船期入口分开 [S09] | 体验时间、抵达成本、最晚返程是不同约束 | 岛上1.5小时就是整项活动总耗时 |
| 北京 Colorwalk | 邻近区域的主题路径和具体文化体验 [S11] | 先构成一个有意义的半日，再填地点与餐饮 | 春季推荐中的限时展览到秋季仍有效 |
| 京都/巴黎/新西兰成品 | 步行链、日期分配、可选活动、住宿基地 [S14–S17] | 按旅行尺度组织内容，明确取舍 | 专业成品的时长合计、开放状态全部准确 |

据此建议把“输出内容质量”定义为：**符合这位用户的目标，能在给定日期与资源条件下执行，并能解释为什么这样安排、如何行动、遇到变化如何调整。** 这是本次设计归纳，不是任何竞品的内部架构声明。

## 两份真实交付物暴露了什么

已从本地端到端产物提取 [baseline-observations.json](baseline-observations.json)，保留原文件路径、SHA-256、Run ID 和观察字段，方便复核。未重新调用模型或交通服务。

**样例 A：`trip_598060a272294789`。** 2026-10-10 至 11 日苏州两日慢游；第一天下午苏州博物馆、晚餐，第二天只有11:30–12:30午餐，17:19返程。午餐结束至发车是289分钟，期间有一段26分钟交通，不能把整个289分钟都算作闲置。午餐理由虽提到“保留充足的返程准备时间”，但未给出这段较长留白的具体用途、时间边界和可选安排，`custom_blocks` 也为空。应补足留白设计与说明，而不是必须再塞入几个景点。

**样例 B：`trip_8bc288c2202e4a0c`。** 四处参观点均为博物馆，分布为第一天1处、第二天3处。这是需要检查体验构成的信号，尚不能判定错误：昆曲、民俗、评弹和科举可能满足文化专题需求。是否不合偏好，应回查完整请求、天气和候选淘汰轨迹，不能仅按名称去重。

**两份样例中观察到的内容问题：**

- 住宿理由使用“承担过夜住宿责任”“受控目的地一致”等内部实现语言，没有解释交通便利性、位置、房型适用性或价格取舍。这是可直接观察的表达缺陷。
- 样例 A 的公交方案由步行—单条地铁—步行组成，却显示“2次换乘”。源码以 `len(segments)-1` 赋值，计算的是段间衔接，不能直接作为公交线路换乘次数。
- 费用结构正确区分已知小计与未知总价，但报告另外展示模型整趟估算：样例 A 已知98元、估算878元。后续需核验估算依据和未计入项目，不应笼统声称“没有预算”或“98元就是总费用”。
- 报告概述固定称“可执行旅行方案”。当预约/价格等仍待确认时，这个统一表述无法体现实际准备程度。

这些样例适合成为回归材料，不能作为两次同配置重复运行的质量对比结果。

## 源码诊断与归因边界

本节路径和行号是调研时的历史证据，不代表当前代码位置；其中 `entities/itinerary_composition_v2.py` 已拆分到 `planning/itinerary/`，不再保留原模块。

| 观察 | 本地证据 | 影响及边界 |
|---|---|---|
| 区域适配、多样性、冗余及交通代价字段是常量 | `services/candidate_ranking.py:159`：1、1、0、0 | 这些字段目前没有区分能力；不等于所有选择完全不考虑位置或偏好 |
| 默认补齐容量按天数/目的地数计算 | `services/candidate_selection.py:207` | 未按每日可用时间、强度、住宿基地计算；必选/覆盖步骤可能突破该容量，不能称全流程硬截断 |
| 骨架先确定停留点顺序，之后研究相邻交通 | `agents/itinerary_planner/node.py:737` | 交通可以检验既定顺序，但尚需更早影响候选组合；先骨架后精查本身不是错误 |
| 分散度只记录 | `services/geo_dispersion.py:1`、`agents/itinerary_planner/node.py:2109` | 已有观测基础，尚未形成选择/修复反馈；不应凭空设全国统一距离门槛 |
| 每个非纯交通日至少一处 Visit/Dining 是底线 | `agents/itinerary_planner/node.py:800` | 能防空结构，不能证明全天有合理内容；餐馆单独满足这条底线 |
| 不足领域提示“已选主方案必须先全部用上” | `agents/itinerary_planner/node.py:764` | 在这个分支会增加填满已选项的压力，需允许基于整日可行性回退选择 |
| 骨架归一化使用30分钟转场窗口，必要时压缩至午夜前 | `agents/itinerary_planner/node.py:1545`、`entities/itinerary_composition_v2.py:244` | 是结构修复，不是个性化节奏或实际门到门时间；后续有 Provider 校验，不能说最终交通一律30分钟 |
| 交付门主要阻断结构问题 | `agents/orchestrator/delivery_quality_gate.py:1` | 丰富度/来源等缺口可被记录后交付；需要单独表达体验质量与准备程度 |
| 换乘次数按分段数推导 | `entities/itinerary_composition_v2.py:3017`、`entities/workspace_v2_mutations.py:952` | 步行接驳不应自动算公交换乘；应有明确交通语义及回归样例 |
| 报告统一声明可执行 | `services/delivery_projection.py:1097` | 输出承诺应依赖检查结果与待办状态 |

**反证必须保留：**`entities/itinerary_composition_v2.py:123` 已验证可解析的景点开放时间，`:1755` 有按已查路线时长和开放边界调整整天的逻辑。因此不能以“完全没有时间校验”为重构理由。它们仍受事实缺失、字符串解析、临时例外、最后入场与预约条件覆盖范围限制。

## 建议的目标流程

```mermaid
flowchart LR
    A[需求与固定订单] --> B[目的地经验和日期事实]
    B --> C[每日区域、核心体验、住宿基地、留白]
    C --> D[候选组合与粗略交通评估]
    D --> E[关键路线精查与时间排程]
    E --> F[可行性与体验检查]
    F -->|局部失败| D
    F -->|通过或明确待确认| G[执行说明、预算依据、预约待办、替代项]
```

这应是现有工作流中的职责补齐，初期不需要增加一组常驻代理，也不需要全面替换合同、事实来源和持久化机制。

1. **先形成每日设计。** 每天表达核心体验、主要区域、可用时间、体力/步行偏好、固定订单、住宿基地和主动留白。一天只做一件事也可很好，但要有依据。到达/离开日不能按完整游玩日算容量。
2. **从独立地点排序走向组合评价。** 保留硬约束优先；对合法候选组合计算相邻交通、重复体验、兴趣覆盖与预算影响。先用地理邻近/缓存做粗筛，精查少量有希望的连接，避免对所有地点两两调用路线服务。
3. **补充规划所需的事实语义。** 区分开放区间、最后入场、预约时段、临时关闭、有效日期；区分游玩时长、排队、接驳、行李、休息。坐标只能证明地点存在，不能证明某日能进、某次有票或适合用户。
4. **让修复回到正确环节。** 交通太远时允许改顺序、换区域或换候选；缺候选才补查；缺预约事实则提供待确认条件和替代方案。修复后继续执行现有硬规则和意图检查，避免无限循环。
5. **最后生成旅行者需要的说明。** 每日解释为什么这样走；每个核心体验说明值得做什么、如何进入、多久、需要提前做什么；提供一种局部备选及触发条件。住宿讲选区取舍，预算讲已知/估算/未计入项目，避免内部字段措辞。

建议在现有模型上逐步表达这些概念，而非一次性把所有候选新增几十个必填字段。名称、值域和存储方式应在实现阶段按真实消费方确定。

## 第一轮工作顺序与验收

| 优先级 | 工作 | 完成证据 |
|---|---|---|
| P0 | 固化失败样例、定位各阶段内容损失；纠正换乘语义和内部术语进入报告 | 有可重放材料；步行—单线地铁—步行为0次线路换乘；说明表达用户收益 |
| P1 | 每日设计与体验检查；区分自由时间和遗漏 | 慢游允许留白；未解释空白被指出；专题旅行不会被强制打散 |
| P1 | 组合评价接入地理/交通/重复体验，允许有限回退 | 同事实候选池下，路线和偏好盲评改善，硬约束通过率不下降 |
| P2 | 日期规则、预约待办、住宿接驳及预算依据 | 临时关闭覆盖旧规则；未知不算已通过；总预算可追溯假设 |
| P2 | 精炼报告与局部 Plan B | 不增加无依据细节；交付状态与事实准备程度一致 |

详细场景、指标和对照方法见 [evaluation-plan.md](evaluation-plan.md)。先在固定事实快照上比较现有流程、仅提示词调整、每日设计/组合反馈，再做真实在线回归。否则无法区分“搜索结果变好了”与“规划能力变好了”。

## 限制与反向检查

- 没有竞品同题生成实测，不能给产品质量排名，也不能声称本建议复制了它们的内部实现。
- 专业成品同样可能有过时地点、时长不闭合或商业推介；使用其组织经验时，仍需重新验证执行事实。[S03、S14–S18]
- 不能以景点数、多样性或填满时间为唯一目标；明确主题、休息、恶劣天气都能合理改变内容构成。
- 目前只有一个目的地的两份本地产物；评测场景是拟定标准，尚未执行，不能宣称收益。
- 直接放宽准入、用模型补造价格/时刻、把所有缺口都变成强制失败，均可能降低真实可用性。应保留来源、预算上限、终止语义和禁忌约束。
- 反向审阅已核对上述常量字段、容量边界、样例事实与现有时间校验；未发现阻止本轮研究的关键问题。架构因果仍等待对照实验。
