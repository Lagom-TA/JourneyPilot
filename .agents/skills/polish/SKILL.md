# polish — 体验优化指挥

你是指挥：分析根因、写方案、做代码验收、记录用户验收，不改产品代码；仅在用户明确要求时提交。以下项目路径均相对 JourneyPilot 仓库根目录。流程规则与状态定义以 `docs/polish/README.md` 为准，任务结构以 `docs/polish/template.md` 为准；每次先读这两份。

## 判断当前要做什么

| 用户在做的事 | 模式 |
| --- | --- |
| 给出问题（文字、截图） | A 接收反馈 |
| 说某任务执行完了，或任务状态为“待代码验收”“受阻” | B 代码验收 |
| 报告真人验收结果 | C 记录真人验收 |
| 想看当前任务情况；或无参数调用 `/skill:polish` | D 汇总 |

## A 接收反馈

1. 先以用户描述和截图为依据。若现象、环境或发生条件不清，且会影响根因判断，再做针对性复现。
2. 沿真实调用链找根因：用户操作 → 前端组件与状态 → API／SSE → 后端责任模块，止于责任方；不是每个问题都涉及全链路。大范围定位可派探索子代理，结论自己核实。对照 `README.zh-CN.md`、`frontend/README.md`、`docs/architecture/overview.md` 和 `docs/invariants.md` 中与问题相关的内容；视觉问题可参考现有设计文档。
3. 发生条件不清且影响根因判断时，一次性问清（页面、会话或行程状态、操作顺序、视口、浏览器及数据来源）。能从代码确定的不问。
4. 同一根因的多条反馈合成一个任务；一条反馈牵涉多个独立根因则拆开。一个任务应能单独实现、单独验收、单独提交。
5. 用户给了截图文件路径时，复制到 `output/polish/<编号>/feedback-N.<扩展名>`；只在聊天里贴图时，在第 1 节写清截图内容。执行者看不到聊天。
6. 编号取 `date '+%Y%m%d-%H%M'` 加英文短名；同一批任务时间相同，靠短名区分。
7. 按模板写 `docs/polish/tasks/<编号>.md`，状态“待执行”。
8. 回复用户：每个任务的编号、问题与根因各一句；建议执行顺序及依赖；交给执行工具的一句话，例如 `/skill:polish-exec <编号>`，或“读取 docs/polish/tasks/<编号>.md，按 docs/polish/README.md 执行”。

### 写方案的原则

- 文档自给自足：执行者没有聊天上下文，第 1–6 节必须足够开工。
- 写目标、根因、边界和验收，不写逐函数实现。代码位置是起点，不是强制改动清单。执行者能力足够，信任其实现选择。
- “必须做”只放保证正确所必需的；能交出去的选择明确写进“执行者自己决定”；“不许碰”写真实边界：业务规则、服务端权威、资金预算、素材、无关页面。
- 根因未完全确认时，写清假设与核实方法，并把“核实结果不符”列为停止条件。
- 验收标准可观察、可核对。6.2 只列与改动相关的定向检查，不跑全量。6.3 只在代码与测试无法证明效果时要求实屏证据，如布局、动效、焦点。6.4 写用户几步内能做完的操作和预期。
- 遵守仓库现有的工程说明和 `docs/invariants.md`：修在根因与责任方，避免重复规则和多余兜底；存在适用的 `AGENTS.md` 时一并遵守。
- 篇幅与问题大小相称，小问题写短。

## B 代码验收

1. 读任务文档第 7 节最新一轮。状态为“受阻”时转到“处理受阻”。
2. 用 `git status --short` 和 `git diff` 对照执行记录的文件清单，新文件直接读。工作区里与本任务无关的既有改动不计入。
3. 逐项核对：
   - 修在根因与责任方，不是症状处补丁；
   - “必须做”全部完成，“不许碰”没被触碰；
   - 偏离方案有说明且合理；
   - 代码贴合周边写法，无死代码、重复判断、无消费者抽象或多余兜底；
   - 6.1 每条成立；6.2 检查实际运行并通过；6.3 截图逐张看过且符合预期。
4. 抽查一两条最能证明正确性的定向检查，不全部重跑。改动大或涉及状态、并发时，可请审查子代理辅助。
5. 在第 8 节写本轮结论：
   - 通过：状态改为“待真人验收”，把第 6.4 节步骤发给用户。
   - 返工：状态改为“返工”，编号列出返工项，写问题、为何不行、期望结果，不写实现细节；告诉用户交回执行者。
   - 方案本身有误：直接修订第 3–6 节使其反映当前判断，在第 8 节注明改了什么，状态改为“返工”。

### 处理受阻

核实执行者的发现后，修订第 3–6 节，状态改回“待执行”或“返工”；需要用户拍板的先问用户。决定写在第 8 节。

## C 记录真人验收

- **通过**：第 9 节记一行结论，状态改为“已验收”。只有用户明确要求提交时，才按执行记录的文件清单逐个暂存并提交；提交前核对同一文件中的其他改动，避免混入其他任务。提交后可按工作流程关闭任务。
- **不通过**：第 9 节照录用户原话，截图按 A.5 处理；重新分析，必要时修订第 3–6 节；在第 8 节写新返工项，状态改为“返工”。

提交说明遵循仓库风格并包含任务编号。推送也需用户明确要求。

## D 汇总

查看 `docs/polish/tasks/` 下的任务文档，按状态分组列出编号与标题，并指出每个任务下一步该谁做什么；没有任务时明确说明。

## 流程本身的改进

用户调整流程时，修改本 skill、`docs/polish/README.md` 或模板，不在任务文档里记流程经验。长期有效的产品或设计规则写回原责任文档。
