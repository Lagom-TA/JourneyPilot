00

一句话架构

旅行规划出错，多数时候不是模型不够聪明，是它编了一个听起来对的东西。

一家不存在的餐厅。一段没人量过的步行时间。一个用户明确说过不要、却还是排进第三天的安排。这些都不是能力问题，是约束丢失。所以这套架构的重心不在提示词上，在四件事上：

  • 把用户意图变成可校验的合同，而不是塞进 prompt 的一段自然语言。归一化只做一次，产出 RequestContract（含 IntentSpec + ConstraintPack + clause 台账），此后所有节点读的都是这份合同。
  • 把「找到什么」和「相信什么」分开。Worker 只负责产出强类型 ResearchPacket；候选是否成立由 candidate_gate 的确定性准入逻辑判定——身份能否落地、价格证据是否可回溯、是否在目的地范围内。模型说了不算。
  • 把时间和钱在授权那一刻封存。用户在计划门点「批准」的瞬间，RunDeadlineSnapshot 与 RunBudgetSnapshot 一同定格。之后任何配置改动都不影响这个已在飞的 Run。
  • 只有一个出口。图上通往 END 的正常路径只有 delivery_finalizer。报告、地图、来源、PDF 全是同一份 TripWorkspaceV2 的确定性投影，所以它们不可能互相矛盾。（还有一条 ask_user 到 END 的边，它不产出交付物，代价见 §13。）
读这张图的方式

全文用三种颜色区分节点性质：青绿＝纯代码/确定性，赭石＝会调用模型，黄铜＝人在环中断。数一眼有几块赭石，就知道这个 Run 有几个地方可能编出东西来。

01

入口与分流

进图之前先有一次判断：这句话该走哪条路。分流本身由模型完成，但它的失败方式是报错，不是兜底。

services/route_intent.py 用 fast 模型把一句自然语言判为四条路之一。这个模块的设计立场写在它自己的文档字符串里：判不出来就抛 RouteIntentUnavailable，由调用方诚实报错，不许拿一条兜底路线冒充结论。ambiguous 只在两种读法确实同等成立时为真，「信息不足」不算歧义——那是规划路径自己会去追问的事。

路径触发去向形态
trip_planning目的地已明确，需要安排深度工作流（本文主体）22 节点 LangGraph
destination_discovery还不知道去哪，要先比较深度工作流（窄计划）只跑 destination 域
trip_refinement改已存在的那趟行程深度工作流 + 修订通道见 §10
fast_answer一条可直接回答的事实快速工作流START → fast_answer_agent → END

快速路径是一张只有一个节点的图（workflows/fast_answer.py）。它有自己的 RAG、自己的 Constraint Pack 装配和输出守卫，并带一个「边界自知」机制：检测到需要深度调研时，主动用任务语言引导用户切换模式，而不是硬答。

02

全景：三段一环

深度工作流是一条三段主链。第一段把请求变成合同，第二段把合同变成经过准入的候选和一份行程，第三段把行程投影成交付物并原子落库。只有第二段有环。

为什么第一段没有分支

这一点是刻意的。scope_clarifier 曾经有一条「模型追问用户」的分支，现在被删掉了：基础旅行事实（目的地、日期、同行、风格）由用户在界面上确认的受控旅行身份带进来，不由模型推断。拿不到身份就抛 ScopeIdentityError —— fail-closed，而不是静默走一条已经不存在的旧路。

结果是：从入口到计划门，整条链的行为完全由输入决定，可以逐节点回放。唯一的模型调用（意图归一化）也被压缩成一次，并且它的输出是强类型的 clause 台账而不是自由文本。

03

运行时钟与预算

时钟不是超时保护，是架构的一部分。四个窗口把一次 Run 切成四个阶段，每一次模型调用都属于且只属于其中一个窗口；窗口一关，对应的调用路径在图上直接消失。

窗口如何改变图的形状

关键在于窗口不是在某处 raise TimeoutError，而是让路由函数返回不同的值。同一个函数在窗口内外返回不同的下游节点：

  • dispatcher：research_closed 后跳过剩余研究组，若行程尚未组合且组合窗还开着，直接跳到组合步骤；否则收束到 to_check。
  • route_after_candidate_gate：research_closed 后，除「精确连接段扫描」这一种属于组合窗的特例外，一律折成 passed。
  • route_after_artifact_gate：越界后一律 accepted，研究与修复路线都是模型路径。
  • streaming_react_loop：每轮迭代开始前调 remaining_model_seconds()，抛 ModelWindowClosed 就带着当前的部分结果返回。

这是「深度防御」：节点里判一次、边上再判一次。原因写在代码注释里——一条在阶段边界前一刻写下的路由，不能在边界之后还打开一个模型 worker。

05

计划门：唯一的正常阻塞点

plan_gate 用 LangGraph 的 interrupt() 把整个 Run 停在 worker 扇出之前。它的意义不只是「让用户确认」——它是时间与金钱的授权时刻。

进门之前先做一次硬合同校验（_validate_plan_gate_contract），任何一项不成立直接 raise，而不是降级放行：

  • 合同不得含阻断级意图冲突，不得含未解决的实质 clause；
  • 每个 active hard intent 都必须在某个 assignment 的 must_cover_intent_ids 里有归属；
  • 每个影响研究阶段的 intent 都必须在 ResearchBrief 里有对应的域目标；
  • MinimumDeliveryDraft / CapabilityPlan 的 generation_id 与 intent_spec_revision 必须与合同对齐。
用户动作门内做什么路由到额度
approveseal_minimum_delivery_draft() — 同时封存 RunDeadlineSnapshot + RunBudgetSnapshotdispatcher—
edit / supplement包装成 IntentAmendment，按影响面调 invalidation_update()request_contract_normalizer（重走合同段）全程 1 次
approve + 附言先判是否「只影响呈现」；是则记为 PROJECTION_ONLY 并在下一轮直接放行同上计入同一次额度
cancel抛 RunCancelled，走取消收束链—任何轮次均可
其它 / 额度用尽后再改视为协议违规，重新 interrupt，不静默兜底回到等待—
这里的设计取舍

修改额度是 1 次。第二轮门只接受 approve / cancel。这是用「有限协商」换「有界成本」：每一轮修改都要重跑整个合同段并作废下游产物，无上限的协商会让时钟在研究开始前就烧掉一半。

准入把「找到了」和「可信」分开

这是候选门最重要的一条设计。天气、预算、约束的匹配程度全部是 0–1 的排序信号，只有具体身份是准入条件。代码注释把理由写得很直白：一个在另一座城市的地点，不是「更差的选项」，它不是选项；而一个贵一点的酒店只是排序靠后，不该因此丢掉这个实体。

同样的分界也体现在证据上：一个必填字段，如果它的真值无法从服务端编译的 source record 重新推导，就当作缺失处理，而不是当作「模型断言过所以成立」。

Worker 内部管线

三个研究 Worker 共享同一套骨架，差别只在工具白名单和预检策略。下面是最复杂的 destination_researcher（1 964 行）。

按需工具曝光（Tool Search）

当工具目录过大时，apply_tool_exposure() 走 deferred 模式：初始只暴露一个 search_tools 元工具，并把压缩目录注入 system prompt；模型按需激活的工具进入 activated_tools 并延续到后续轮次。白名单本身不变——它既是执行 allowlist，也是 search_tools 的检索边界。deferred 模式会额外补 1 轮迭代预算，避免「按需曝光」牺牲研究深度。曝光决策记入 ToolExposureLedger。

itinerary_planner 的三个相

它是唯一用 primary 模型 + 严格 JSON Schema 的 Worker，也是唯一没有 ReAct 循环的——streaming_react_loop 在它的文件里从没出现过。它被拆成三个由 state 决定的相（_composition_phase()），相之间通过产物交接，不靠某个门记得写一条消息：

相触发条件做什么产物
placement_skeleton无 skeleton只排「不含市内交通」的骨架；违规时可再发一次受限的「锚点移动」结构化调用placement_skeleton
materialize_connectors有 skeleton、无 workspace抽相邻缺口 → 已有路线填充 → 剩余缺口由模型 authored → 物化为 workspacetrip_workspace_v2

每一次确定性后处理（去重、补位、锚点移动、连接段物化）都记一条 CompositionMutation，进入 workspace 的变更台账——所以「模型写了什么」和「代码改了什么」在交付物里是可区分的。

第三段 · 交付

交付段不做任何判断，只做投影和落库。所有面向用户的界面——报告、地图、来源索引、PDF——都是同一份 TripWorkspaceV2 的公共安全投影，因此它们不可能互相矛盾。

为什么「只有一个出口」是架构约束而不是巧合

如果 END 有多个入口，就会存在「已经给了用户东西但没落库」或者「落库了但 workspace 不完整」的状态组合。单出口 + 原子提交把这些组合直接从状态空间里删掉。图上另一条到 END 的边（destination_researcher 的 ask_user HALT）不产出交付物，它是一个挂起的 Run，等用户回答后从 checkpoint 续跑。

10

横切 · 修订通道

用户可以在 Run 跑到一半时追加要求。这条路径不直接改 prompt——它先变成 IntentAmendment，回到同一个合同边界重新归一化，再按影响范围精确作废下游产物。

实现方式很直接但很有效：travel_planning.py 里几乎每条边都被包了一层。_route_after_boundary(target) 返回的路由函数先看 state.pending_intent_amendments，有就转去 intent_amendment_router，没有才走原目标。intent_amendment_router 的合法续跑目标是全部 20 个节点——所以修订可以在图上任何一个安全边界被接住，并从最合适的位置继续。

不支持的请求会被显式拒绝

intent_amendments.py 里有一张 _UNSUPPORTED_CUES 表（「代订」「预订并付款」「购买机票」…）。命中的追加要求变成 IntentAmendmentRejection 记录在案，而不是被模型「尽力而为」。这与产品边界一致：JourneyPilot 交付计划，不执行交易。

横切 · 控制、治理、记忆

运行控制：进程内是缓存，库里是事实

with_run_control(node_name, fn) 包住每一个节点，提供三件事：取消检查、运行归因（run_id / node / agent 的 contextvar + 单调钟锚点）、节点生命周期事件。run_control.py 的文档字符串把定位说得很清楚：这个模块只是进程内的低延迟通道；最终事实在 trip_runs（业务状态）与 trip_run_commands（控制命令）。registry 不回答「有没有这条命令」，只回答「这个进程现在跑着这个 run，可以马上去读表」。通知丢了最多多等一个轮询间隔。

工具治理：每次调用都留一个信封

工具不是直接调的，走 ToolGateway。每次执行产出一个 ToolExecutionEnvelope：参数摘要与哈希、来源与信任级别（infer_trust_level）、结果摘要、新鲜度提示、权威度评分。两件事由此成立——

  • 注入扫描：_scan_tool_result_for_poisoning() 对不可信来源的返回内容做提示注入检查；is_untrusted_tool_content() 按来源 + 服务器 + 工具名判定。

记忆：深度路径上只有一条注入通道

这一点在代码里被反复强调，因为它曾经不是这样。深度路径上模型真正读到的记忆全部经由 Constraint Pack（panels/constraint.py::format_constraint_pack_for_prompt）。此前 scope_clarifier 也装配了一份完整的五层记忆 prompt——而那份 prompt 一个字都没进过任何模型调用：同一个角色两套装配，其中一套静默胜出，另一套每轮照付一次库查询与一次 token 计账的钱。

现在的分工是：scope_clarifier 只量会话大小（历史消息 + anchor + 基础 system），偏好与画像的开销落在 worker prompt 上、不在会话轴上累积——把它们算进压缩阈值反而会让压缩在错误的时刻触发。记忆的内容由 Constraint Pack 的「参考级背景」一节带进 worker prompt。

RAG：每件事只做一次，最后做的那件说了算

retrieval_pipeline.py 的重构说明本身就是一份很好的架构文档。旧形状是「按集合循环，循环体里做全套」，导致三个同族缺陷：改写与 HyDE 被重算 N 遍、精排按变体各跑一次、合并时按 RRF 分排序从而让刚花钱买到的精排顺序完全不生效。新形状是：

步骤次数说明
expand_query每查询 1 次不是每集合一次
retrieve(变体 × 集合)纯检索不在这一步精排
rrf_fuse1 次被越多变体/集合命中的排越前
rerank(原始 query, 候选池)每查询 1 次用原始 query 而非变体；它就是最终顺序

之上还有 RAGModePolicy：按查询风险（签证/价格/营业时间/实时）、口语程度、探索性决定是否启用改写、HyDE、CRAG 分级与精排——不把每个查询都当成完整的 advanced-RAG 路径。

观察到的形状

下面几条是读代码时记下来的，只写现状和它的代价，不下结论。前三条经过第二轮复核，说法和第一版不一样了。

一、图是静态的，计划是投影出来的

execution_plan 由 build_capability_plan() 投影出来，模型不参与。它实际上只有两种形状，而且两者只差一个住宿 worker：destination 和 transport 是结构强制的（capability_planning.py:89 无条件加长途交通域，product_requirements.py:128 让 visit 恒在），itinerary 也是无条件加的。

换句话说，每一次深度 Run 都走同样的三步。代价很直接：「深度玩两个博物馆」和「把七个城市的火车串起来」拿到的是同一条管线、同一套工具白名单、同样的轮次上限。

二、Worker 是「一次性产出强类型对象」，不是「持续工作的 agent」

三个研究 Worker 的生命周期是：装配 messages → 跑 ≤N 轮 ReAct → 定型成一个 packet → 结束。itinerary_planner 不走这条路，它是一次带 JSON Schema 的结构化调用，没有循环。两类都不保留自己的记忆，不能中途改自己的目标，也没法要求「再给我一轮」。

补研由门发起。这里有一点容易记错：门写进 state 的是 assignments[worker]——base key，直接覆盖上一轮那份。round suffix 是 Worker 节点自己生成的，只用在产物键上（utils.py:394-416）。所以 assignment 里没有逐轮记录，第 N+1 轮看不到第 N 轮试过什么、怎么失败的。

三、修复预算是离散计数，不是效用判断

每域 1 次定向补研、全 Run 3 次组合修复。composition_repair.py 的文档字符串记录了为什么从 1 改成 3：骨架合同是一组互相独立的硬规则，模型每轮违反不同的一条；1 次不是边界，是抛硬币。同一份 docstring 还说了句更要紧的话：真正的边界一直是墙钟，这个计数只是在一个别处已经强制的窗口里多买几次重试。

另外，「每域 1 次」是下限不是上限：_domain_research_budget() 会按航段数、目的地数、邻接缺口数放宽（candidate_gate.py:1458-1502）。它按受控身份给的责任数算，不按尚未满足数算——docstring 讲了理由：账本是累积的，随满足度收缩会在最后一个责任最需要第二次机会的那一秒把它拿掉。

四、门之间的知识是通过 state 字段传递的，不是通过接口

TravelAgentState 有 97 个字段，其中 15 个是路由与门之间的协议载体（candidate_gate_route / artifact_gate_route / intent_fidelity_route / delivery_quality_route / candidate_gate_failure_signatures / gate_failure_attributions / composition_repair_attempts …）。artifact_gate 直接从 candidate_gate import 了三个符号，其中 _latest_packets 带下划线。全仓这种跨模块私有导入只有三处，agents/ 下就这一处。

五、错误分类是一条隐式契约

last_error 是一个字符串，但它的前缀（provider_empty: / provider_capability: / schema_gate: / provider_transient: / provider_deterministic:）是门判定补研预算的判据。写入方是 format_worker_last_error()，读取方是 classify_provider_failure()，中间只有字符串约定。

它的 reducer 是 _prefer_non_empty_str（后到的非空值胜），而 dispatcher 用 Send() 真并行扇出。candidate_gate.py:1685 的注释把后果写在那儿了：无法区分并发 worker 的失败。

六、代码注释承担了架构决策记录的职责

这个仓里大量注释不解释「这段代码做什么」，而解释「为什么不是另一种写法」，常常带上具体的失败 run id。composition_repair.py、retrieval_pipeline.py、scope/node.py 的模块 docstring 本身就是能读的 ADR。副作用是这些决策的上下文主要活在注释里，不在 docs/adr/。
